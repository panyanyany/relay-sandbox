# 保留和复用项目环境

状态：开发版已实现。新任务默认复用同一注册项目的持久 Docker 容器。任务和环境分别记录；旧任务不会自动迁移为持久环境。实际验证范围见[实现验证记录](implementation-validation.md)。

## 选择保留方式

在项目的 `relay-sandbox.yaml` 设置：

```yaml
environment:
  mode: persistent
  idleRetentionHours: 24
```

| 模式 | 行为 |
| --- | --- |
| `persistent` | 默认。保留环境，直到用户明确删除或重置；不按任务的 24 小时保留期删除 |
| `ttl` | 环境释放后开始计时，空闲超过 `idleRetentionHours` 时由 `gc` 或监督器删除 |
| `ephemeral` | 创建一次性环境；成功交付后自动销毁运行时，异常或取消后用任务清理入口销毁 |

同一项目环境一次只允许一个任务借用。不同项目分别保存。任务完成后停止进程、回收通信代理和证书，再释放环境。停止会保留容器可写层中的软件、用户配置和文件，不保留进程内存。日志继续按各自保留期轮转，不随环境永久增长。

失败、尚待审核或发生同步冲突的任务可能继续占用环境。先检查结果并执行 `cleanup <任务ID>`，再开始下一任务。取消使用 `cancel <任务ID>`；取消后环境停止并释放，同一旧任务只有在环境尚未被其他任务使用时才可 `resume`。

## 同步下一任务的项目内容

默认隔离模式在新任务开始时生成新的宿主项目快照，再与环境工作区做三方同步：

1. 使用上次同步的宿主快照作为共同基线。
2. 将宿主新增、修改和删除同步到工作区，同时保留未冲突的环境内容，例如安装生成的依赖目录。
3. 双方冲突时明确失败，不覆盖原项目，也不继续派发开发 Agent。
4. 成功交付后再次同步已应用结果并更新共同基线，使下次宿主删除上轮新增文件也能正确传播。
5. 将同步后的实际工作区记录为本任务开发基线。既有依赖不会仅因复用而算成本轮新增成果。

Git 管理目录使用本轮宿主副本，不继承上轮工作区可能修改的 Git 配置或 hooks。排除规则仍控制宿主初始内容交付，不保证过滤开发过程中生成的文件。直接挂载模式继续读写原项目，不执行隔离工作区替换。

同步失败后保留任务现场，并标记环境需要重置，防止半写入工作区被当作成功同步。先取回需要保留的内容、清理失败任务，再显式重置。镜像、项目目录身份、工具类型、资源限制、排除规则、挂载或冻结权限变化时也要求重置；不自动迁移或静默重建环境。

## 停止、重置和删除

构建后使用 CLI，`<项目ID>` 是已注册标识：

```sh
node dist/src/cli/main.js environment-status <项目ID>
node dist/src/cli/main.js environment-stop <项目ID>
node dist/src/cli/main.js environment-reset <项目ID>
node dist/src/cli/main.js environment-delete <项目ID>
```

MCP 对应工具为 `get_environment`、`stop_environment`、`reset_environment`、`delete_environment`，参数是 `project`。

- 停止保留文件。活动任务须先取消，不能用空闲环境入口绕过任务状态。
- 重置删除空闲环境，下一任务按当前基础镜像重新创建。
- 删除回收环境容器、网络和环境私有副本，不删除宿主原项目、已授权源、任务报告或备份。
- 重置和删除仅由用户明确要求。宿主 Agent 不应在普通收尾中自动调用。

`cleanup_task` / `cleanup` 只清理该任务资源，并停止、释放其借用的持久环境。旧任务清理会核对当前借用者，不能停止或删除下一任务使用的开发容器。TTL 回收在删除锁内再次核对空闲时间，避免过时计划误删新借用环境。

## 核对审计与历史状态

持久环境中的可疑配置、启动文件和已安装程序也会留下。新任务报告明确提醒历史状态；环境复用不表示历史软件安全。需要干净环境时显式重置。

诱饵开启时，环境保存同一组假值，避免下一任务无法匹配旧诱饵。每任务生成新的代理和证书，历史安装位置标为未重新确认。旧任务的通信事件不计入新任务；敏感行为审计和审核摘要继续按任务保存。不保存进程内存或真实宿主凭据。

## 排查和实现边界

环境元数据位于宿主状态目录的 `environments/<项目ID>/environment.json`；软件本身位于 Docker 容器可写层。目录中还保存同步基线、额外资源副本及可选诱饵身份，不提交到项目仓库。

环境操作使用排他文件锁。控制进程崩溃留下 `operation.lock` 时，先核对锁中进程已退出，再由操作者移除；不会自动抢占。独立监督器仍须运行，才能处理失联任务和 TTL。当前不提供磁盘硬配额、环境备份迁移或断电时同步事务恢复。Docker 容器被外部删除时明确报错，需显式重置，不能声称环境内容仍然存在。

## 核对候选检查与故障记录

持久环境的候选检查在开发容器停止后，将实际使用的额外 `copy` 资源冻结到任务的 `check-resources/`。检查容器使用独立副本；检查写入不影响持久环境或宿主授权源。再次检查时重新冻结。`direct` 资源保持原有直接访问语义，不改成副本。一次性环境继续使用原任务资源规则。

诱饵清单或历史摘要损坏时，任务记录 `persistent-audit-unavailable` 覆盖缺口，并保存脱敏诊断。普通开发继续；本任务的恢复和候选检查也跳过诱饵安装，不能重新生成假值并声称历史匹配有效。覆盖缺口无法保存时任务明确失败。修复状态文件后可创建新任务，或按需显式重置环境。

工作区同步与停止同时失败时，使用统一收尾工具保留两个错误。创建失败的任务记录保存完整脱敏错误链，包括准备错误和收尾错误；专用模型凭据不进入错误记录。回归测试和验证结果见[实现验证记录](implementation-validation.md)。
