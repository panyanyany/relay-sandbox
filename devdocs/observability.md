# 回溯沙箱状态并清理资源

任务创建后自动启动独立宿主采集进程。采集器不运行在沙箱内，也不依赖宿主 AI 持续轮询。沙箱进程退出后，宿主仍可记录退出状态。宿主整机断电、Docker 长时间不可用或采集器本身被杀死时，采样会有缺口，不能据此还原间隔内的全部行为。

## 配置采样和保留

在项目 `relay-sandbox.yaml` 中设置。任务创建时冻结配置：

```yaml
logging:
  sampleIntervalSeconds: 10 # 1–60 秒；请求耗时会增加实际间隔
  maxFileBytes: 1048576 # 指标单文件最多 1 MiB
  maxFiles: 5 # 包含当前指标文件，最多 5 个
  retentionDays: 7
lifecycle:
  finishedRetentionHours: 24 # 结束、失败或停止任务的资源保留期
  interruptedRetentionHours: 24
audit:
  reportRetentionDays: 7
```

指标轮转上限适用于 `telemetry/samples.jsonl` 及数字后缀归档，不是整个任务目录的磁盘硬配额。单条采样超过文件上限时明确记录采样错误，必要时增大文件容量。

## 读取指标

```sh
node dist/src/cli/main.js --home <状态目录> metrics <任务ID>
```

MCP 使用 `get_telemetry`。`get_result` 也包含采集状态与最后一条采样。任务目录中：

| 文件                               | 内容                                       |
| ---------------------------------- | ------------------------------------------ |
| `telemetry/samples.jsonl`          | 周期采样，按容量轮转                       |
| `telemetry/samples.jsonl.1` 等     | 较早的指标记录，达到数量上限后删除最旧记录 |
| `telemetry/latest.json`            | 最后一次采样或明确的采样错误               |
| `monitor-worker.log`               | 采集进程启动或致命错误                     |
| `events.jsonl`                     | 任务阶段变化                               |
| `round-N.log`                      | 开发 Agent 每轮完成后保存的脱敏输出        |
| `audit-events.jsonl`、`audit.json` | 敏感访问证据及覆盖缺口                     |

每次采样按任务标签读取开发、检查、服务和通信观察代理容器。记录任务阶段、轮次、时间、容器状态、退出码、OOM 标志、重启次数、CPU 百分比、内存用量和上限、PID 数量、网络收发累计字节及块 I/O 累计字节。不采集文件内容、环境变量值或凭据。

CPU 使用单核 100% 口径，多核占用可大于 100%；第一条缺少有效基线时为 null。内存使用 Docker 原始 usage，包含其计入的缓存，不等同于工作集。不可获得的指标为 null，不显示为零。I/O 字节不是磁盘已用空间。进程短于采样间隔时可能没有指标记录，不能代替内核审计。

## 清理运行资源

正常收尾调用 `cleanup_task` 或 CLI `cleanup <任务ID>`：先停止指标采集，再独立尝试删除本任务开发、检查、服务、观察代理容器和网络。全部运行资源回收成功后，才删除基线、结果、候选、授权资源副本和主诱饵清单。失败时保留错误和可重试状态，不标为 cleaned，也不提前删除资源副本。授权源不在删除清单中。指标、审核、审计和应用备份先保留，便于回溯。

自动到期回收需要独立运行监督器：

```sh
node dist/src/cli/main.js --home <状态目录> supervise --interval 5
```

监督器重启死亡的任务采集进程，协调失联任务，并定期执行到期清理。当前不会安装系统服务，部署时须通过自己的进程管理器保持监督器运行。

也可以手动或由调度器执行：

```sh
node dist/src/cli/main.js --home <状态目录> gc --dry-run
node dist/src/cli/main.js --home <状态目录> gc
```

预览列出本状态目录中的到期任务资源、报告、指标文件和 TTL 项目环境。默认持久环境不按任务保留期限删除，任务资源清理会停止并释放环境；只有 TTL 到期或显式环境删除才回收其开发容器和网络。详见[持久环境](persistent-environments.md)。回收时跳过仍有存活操作进程的任务。等待用户处理、被审核阻止及就绪候选不自动按结束时间销毁，需要显式收尾。结束、失败和停止任务在 `finishedRetentionHours` 到期后清理；中断任务按 `expiresAt` 清理。已清理任务的审计、轮次/后台日志和用户报告按 `audit.reportRetentionDays` 删除。指标按 `logging.retentionDays` 删除，采集器运行时也清除过期指标。

代码备份、任务元数据和清单不会自动删除，便于处理部分应用和后续用户修改。构建镜像不会随任务清理，也不运行全局 Docker prune。磁盘硬配额、宿主断电恢复及所有资源超限场景仍需后续专项验收。

## 回收通信观察资源

任务标签覆盖开发、检查、服务和流量代理容器，指标采集枚举这些容器，不把代理开销隐去。代理本身不保存Docker业务日志或flow文件；最小事件和缺口各按1MiB、3段轮转，报告说明轮转和读取上限。

`stop` 回收任务代理及其私密清单副本、证书私钥，保留主诱饵清单供恢复。`cleanup` 进一步删除主诱饵清单和任务资源副本，保留授权源与宿主备份；报告保留期到期后回收流量证据，保留最小摘要。半启动环境和带本任务标签的孤儿代理也在清理范围内。

停止、删除或网络回收失败会留下错误及可重试状态，不标为全部成功。强制边界异常触发任务停止；内容观察代理异常只更新覆盖状态。周期检查需独立监督器运行，采样间隙和代理退出到下一轮检查之间不保证即时报告。

## 核对停止、恢复和到期回收

2026-11-02 的真实 Docker 测试已验证以下行为，证据范围见[实现验证记录](implementation-validation.md)：

- 停止观察代理后，监督器将观察状态降为 unavailable，开发容器继续运行。
- 强制网络辅助镜像不存在时，监督器实际停止任务容器，再记为 interrupted。
- 恢复使用冻结网络授权和原诱饵清单，创建新的观察运行目录；宿主后续配置变化不扩权。
- 外部测试端点占用任务网络使 cleanup 失败时，任务保留资源副本；排除故障后可重试。
- 报告到期后清除有摘要或无摘要运行目录中的固定 evidence 子目录，保留 summary、任务元数据及备份。普通文件不当作运行目录；链接和非法运行目录名明确报错。单项失败仍尝试其他目录，但不标记报告已回收。

停止错误分支另用真实容器加指定 stop API 503 模拟验证：失败主容器仍运行，其他容器已停止，任务不误报 stopped。它不证明 Docker daemon 自然故障场景。当前 Docker 对暂停容器的 stop 会成功，该探测不计为停止失败证据。

## 处理损坏环境记录与降级诊断

代理和私密材料确认回收后隔离坏元数据，保留诊断并支持重复清理。诊断文件按报告保留期回收；读取预算及错误示范见[维护性修复](maintenance.md)。

## 预防并排查退出码 137

退出码 137 是强制终止线索，不能单独证明内存不足。先使用 MCP `get_telemetry` 或 CLI `metrics <任务ID>`，核对以下证据：

| 证据 | 位置与解释 |
| --- | --- |
| 开发进程结果 | `telemetry/execution.json`：本轮退出码；137 标记为原因尚未确认 |
| 宿主主动停止 | `telemetry/stop-<来源>.json`：取消、超时、监督、收集、交付、恢复、失败收尾等来源，每类保留最近一次请求及结果 |
| Docker 事件 | `telemetry/runtime-events.jsonl` 及轮转文件：OOM、kill、die、stop、start、destroy、exec_die 的最小字段，不保存命令和完整标签 |
| 事件覆盖 | `telemetry/events-status.json`：connected、unavailable 或 stopped；断流记录缺口并重连 |
| 内存峰值与计数 | `telemetry/samples.jsonl` 中的 Docker 内存峰值、分配失败计数及 cgroup v2 的 memory.peak、memory.events（可用时） |

事件流独立于定时采样，减少漏掉瞬间 OOM 的机会。cgroup 读取先核对容器身份；旧内核、权限不足、容器停止或路径不能确认时明确返回 unavailable。计数和峰值属于容器生命周期，持久环境的历史值不能直接归因到本轮。Docker 的容器 OOM 标志也不能代替所有子进程的 OOM 证据。任意进程自行发送的 SIGKILL 不保证能确定发送者。

停止记录先尝试落盘，再执行停止，最后记录结果。诊断写盘失败仍会执行停止，并报告保存错误。超时会停止整个容器，等待正常退出的宽限为 3 秒；没有禁用 OOM 保护或自动提高资源额度。

在项目配置中调整持续高内存提醒：

```yaml
logging:
  memoryWarningPercent: 85
  memoryWarningSeconds: 30
```

默认连续有效采样达到 85% 且持续 30 秒后发布资源提醒。百分比使用 Docker 原始内存，包含其计入的缓存。缺样、进程停止或压力解除会清除持续计时。提醒包含触发时百分比；采样间隔影响实际触发时间。

`get_task` 直接提供 `resourceWarnings`；`wait_task` 和任务资源通过 `task.resourceWarnings` 提供。进入或退出高压会改变快照游标并通知已连接订阅者。宿主应读取指标、提醒用户，并在后续指令中减少浏览器、标签页和构建并行度。提醒不会自动中断内层命令，也不保证唤醒宿主 AI。开发提示已要求有限并发、复用浏览器、及时关闭页面，并按阶段保存产物与进度。

事件日志沿用指标容量与保留策略；停止记录每类固定一个文件，随指标保留期清理。用户报告包含开发退出码、停止记录和当前资源提醒。历史任务没有这些记录时返回缺失，不能反推旧的 137 原因。

## 查看保留的故障证据

`events-status.json` 区分最近生命周期事件 `lastEvent`、最近 OOM `lastOom` 和最近故障 `lastIncident`。普通 kill、成功 die 和成功 exec_die 不替换故障摘要；异常退出仍记录为故障。后续异常退出不会删除独立保留的 OOM 记录。

监控重启读取已有摘要并保留原容器与事件时间，同时标记停止期间的覆盖缺口。断流重连后 `lastGap` 仍保留最近缺口，connected 只表示当前连接已建立，不表示历史覆盖完整。原始事件日志仍按容量轮转。

最终用户报告展示事件采集状态、最近缺口和保留的故障证据，并列出本轮宿主停止来源。事件可能属于旧容器或历史轮次，报告明确要求结合本轮时间核对；有 OOM 事件不等于已经证明它导致本轮退出137。普通成功探针和事件采集时间更新不改变关键事实版本；故障或覆盖变化会使旧回执失效。

## 核对采集器启动锁

创建和恢复任务都会启动独立采集器。`monitor.lock` 先写入完整临时文件，再使用排他硬链接发布；轮询进程只会读到完整 JSON，竞争发布不覆盖已有锁。PID 和进程启动身份仍须匹配。锁文件真正损坏时继续报告解析错误，不把损坏状态当作采集器未启动。
